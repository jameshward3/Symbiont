# Product definition standard

Maintain one stable product ID and immutable version IDs. A definition must contain name, target client, client problem, intended outcome, use cases, scope, exclusions, deliverables, acceptance criteria, client responsibilities, required inputs, dependencies, delivery method, configurable options, estimated duration, cost drivers, pricing inputs, quality plan, security requirements, support model, recurring component, success metrics, evidence, owner, semantic version, lifecycle status, shared goal, projects, opportunities, clients, decisions, and correlation ID.

## Scope and acceptance

State included work as observable outputs. State exclusions with the client consequence and change path. Avoid “as needed,” “complete,” or “industry standard” unless a measurable definition follows. Each deliverable must have a test method, threshold, evidence artifact, reviewer, and disposition.

Configuration options vary approved parameters without changing the intended outcome or core delivery method. Anything that changes the outcome, acceptance basis, safety/security posture, or delivery model is a change or a new product hypothesis.

## Version control

Create a new version for material scope, outcome, interface, acceptance, security, support, economics, or claim changes. Preserve predecessor and change summary. Only an approved current version may be proposal-eligible. Draft versions may be compared or validated but never represented as approved.

## Claims and evidence

Link each performance, savings, ROI, adoption, quality, margin, and recurring-revenue claim to a source, observation window, baseline, method, and confidence. Refuse unsupported claims and replace them with a hypothesis plus validation plan.
